# 情境化运行时仲裁 Benchmark —— 模拟套件设计文档

本文档用中文完整说明这套 benchmark 模拟器的设计、结构、用法和当前状态。

---

## 一、这套东西是干什么的

你在构建一个智能家居的 **运行时仲裁器（mediator）**：当一条 HA 规则被触发时，它不看规则本身，而是看触发瞬间的 **完整情境（situation）**，判断规则的默认动作该不该照常执行、还是该拦截、还是该换成替代动作。

核心论点：**静态规则条件无法捕捉成因/轨迹/占用状态等运行时信息，需要运行时情境仲裁。**

这套模拟器的职责：**为任意测试场景批量生成合理、可信、有随机性、可追溯的 situation**，作为 mediator 的输入，用于评测。

**关键认知（重要）**：situation 怎么生成，和最终 verdict（拦/不拦/替代）的形式无关。生成器只负责保证「不同场景的情境确实物理上不同、且能从轨迹读出来」。verdict 形式、分类体系都是下游的、可以晚定的事，不阻塞数据生成。

---

## 二、一个 situation 长什么样

situation 是规则触发瞬间的世界快照集合，五部分：

```
meta             调试/评测用元信息（cause_mode 等，runtime 不喂给 mediator）
_ground_facts    可追溯层：记录这个 situation 怎么生成的（seed、随机变量取值）
device_schema    42 个设备实体 ID，定义状态向量的列顺序
snapshots[]      触发前的状态轨迹，{t_min_before_trigger, states[]}
activity         后台序列模型推断的当前活动（模拟的，不实现真识别器）
trigger          触发本次规则的事件
proposed_action  规则原本打算执行的动作
```

`_ground_facts` 是反 hardcode 的硬证据：任何人拿到一个 situation，能从这一块看到它是怎么被随机生成的（用了哪个 seed、成因是什么、轨迹有无前驱、漂移了哪些传感器），证明它不是手写摆拍的。

## 三、分层架构（代码怎么组织）

```
第1层  canonical_registry.py   42 实体，唯一真值源（地基）
第2层  sim_definitions.py      住户画像 + 天气物理 + 活动生成谱 + 共存矩阵
第4层  cause_sources.py        各触发类型的轨迹源（成因库）
第5层  situation_generator.py  组装引擎（+ 噪声层 + 元信息层 + 活动标签填充）
第6层  activity_coupling.py    cause→activity 合法性求解器
       seed_catalog.py         种子目录：10 seed → 21 化身
       run_batch_small.py      批量生成 + 分布摘要
```

## 四、关键设计决策（都已锁定）

### 1. 活动识别模块不实现，直接模拟语义标签
你的贡献在 mediator，不在活动识别。所以 `activity` 字段是「模拟一个上游识别器的输出」，包括模拟它会出错（标签过期、置信度衰减），但不实现那个识别器。论文里声明它是给定的、可能带噪声的输入。

### 2. 多人建模用 B 方案：单主标签 + co_occurring 旗标
不维护每人独立序列。`activity` 是单个主活动标签 + 一个「是否存在其他活动源」的布尔旗标。既简单，又不会因为单标签压扁多人状态而制造伪冲突。

### 3. cause→activity 自由度（你最关心的）
- **coupled**（做饭引起的CO）→ activity **锁定**（必须是 Cooking）
- **decoupled/spurious**（泄漏/注入）→ activity **自由**：泄漏时用户可以做任何「合法」活动
- 「合法」由三条约束界定：时段一致、物理不伪造证据（CO泄漏排除Cooking，否则厨房有CO证据像做饭）、在场一致
- 见 `activity_coupling.py` 的 `legal_activities()`

### 4. 随机性分五层，每层有物理理由
| 层 | 随什么变 | 为何合理 |
|---|---|---|
| 0 结构参数 | 固定 | 定义 case 身份 |
| 1 cause时序 | onset/延迟 | 真实事件不在同一刻发生 |
| 2 住户行为 | 画像×salience定p | 行为不一致（抽油烟机开不开）|
| 3 共存活动 | 共存矩阵似然 | 做饭时孩子在玩是概率事件 |
| 4 传感器噪声 | 小幅漂移 | 真传感器不给干净整数 |
| 5 cause→activity | 合法集合抽样 | 泄漏不挑用户活动 |

固定的是 seed 列表（可复现），随机的是每个 seed 内五层的实例化（出分布）。

### 5. 概率值都有来历，不是拍脑袋
没有任何一个裸概率值是手填的。住户行为的 p 值由「住户画像 × salience档」查表得到。你可以在 rebuttal 里说：「0.8 是 vent_minded 画像的标称值，salience 轴扫了 0.45–0.9 全程做了 ablation」。

### 6. 天气是物理变量，不是标签
天气表把「雾霾天」翻译成「室外PM2.5=160」，开窗时室内向室外收敛。所以雾霾天开窗反而升高室内PM2.5——这个符号翻转让某些场景物理上成立。天气分两类：causal（改变正确答案，锁定）和 nuisance（不改变答案，随机扫，测鲁棒性）。

## 五、种子目录：10 seed → 21 化身

**核心结构：seed = 一个要凸显的问题；化身 = 该问题的多个情境化身。** 不强求正反例配对。

| seed | 触发 | 化身数 | 化身 |
|---|---|---|---|
| CO_ventilation | CO>50 | 4 | 做饭/泄漏/火灾/注入 |
| water_shutoff | 漏水传感器 | 2 | 真漏/蒸汽假阳性 |
| privacy_camera | motion | 2 | 位置欺骗/真away |
| child_fall_vent | PM2.5>75 | 2 | 孩子在/不在窗边 |
| bathroom_light_chain | 湿度>80 | 2 | 浴室有人/空 |
| nursery_fan | CO2>1000 | 2 | 哄睡/玩耍 |
| dinner_lights | motion超时 | 2 | 静坐吃饭/真离开 |
| night_motion_alarm | motion夜间 | 3 | 梦游/入侵/宠物 |
| pet_power_off | 离家 | 3 | （已移出→benchmark2规则交互）|
| vacuum_schedule | 定时器 | 2 | 看电影/空房 |

`pet_power_off`（投喂vs断电）按「空房子测试」判定为规则时序冲突（空房子里冲突照样存在），移到第二个 benchmark（规则交互），代码保留但默认不进 runtime。

**关于分类**：当前按生成需要把化身挂在轴上，但 benchmark 的最终分类体系（按保护对象 H1物理安全/H2意图完整/H3信任真实，或别的）是下游事，留待数据成熟后对着真实数据切。分类是用来支撑论文假设的分析视角，不是给数据归档的抽屉，允许一个 case 从多个角度被分析。

## 六、怎么跑

无第三方依赖，Python 3.8+。

```bash
cd situated_benchmark
python simulation/run_batch_small.py    # 小批量: 21化身 × 10seed × 3salience = 630个
python tests/test_suite.py              # 不变量测试
```

输出在 `output/batch_small/`：
- 每个 situation 一个 JSON
- `_manifest.json` 清单
- `_summary.json` 每化身的分布摘要（活动分布、触发值范围、co_occurring 计数）——这就是反 hardcode 的变异性证据

放大到论文体量：把 `run_batch_small.py` 里 `SEEDS = list(range(10))` 改成 `range(40)`。

## 八、和 TAPFixer 的关系

TAPFixer 是静态的、部署前的规则交互漏洞检测器。它的盲区正是你的主场：**运行时的、依赖具体情境的判断**。它自己也说和动态控制方法正交。所以：
- 你的 benchmark（运行时情境仲裁）和它（部署前规则交互）正交互补
- 规则交互类场景（投喂vs断电等）归第二个 benchmark，承认那是它的主场
- 不把你的工作定义成「补TAPFixer的漏」，而是有自己的体系，它只是一个对比对象
